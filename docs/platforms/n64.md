# Nintendo 64

Status: synced

## Identification

| Slug | Inputs | `title_id` example | `usage` | Status |
|---|---|---|---|---|
| `n64` | `.z64` (big-endian), `.v64` (16-bit swapped), `.n64` (32-bit swapped) | `NSME` | file-prefix | |

`title_id` and `raw_serial` are the cart header's game code at 0x3B:
category, game and region. Homebrew and unlicensed carts often carry no
code, and get an empty `title_id`. Verified against 498 dumps: every
licensed cart reads, and Ocarina of Time's 1.0 to 1.2 share one code,
as they share one save format.

Extract also fills `n64_header` (the cart's name, empty when it isn't
plain ASCII, as on Japanese carts that use half-width katakana) and the
ROM's MD5 in two byte orders: `n64_md5` in `.z64` order, as mupen64plus
and M64Plus FZ hash it, and `n64_md5_n64` in `.n64` order, as Project64
hashes it. That reads the whole ROM once, at import. Store them with the
result; the standalone emulators name saves from them.

## Save layouts

| Layout | Files (role, option) | Shared | Verified |
|---|---|---|---|
| `mupen64plus_next` | `{stem}.srm` (primary) | | emulator source |
| `parallel_n64` | `{stem}.srm` (primary) | | emulator source |
| `mupen64plus_standalone` | `*-{n64_md5_8}.eep`, `.sra`, `.fla` (primary); `*-{n64_md5_8}.mpk` (sidecar) | | emulator source |
| `m64plus_fz` | `GameData/*{n64_md5_lower}/SramData/*.eep`, `.sra`, `.fla` (primary); `*.mpk` (sidecar) | | emulator source |
| `project64` | `Save/*-{n64_md5_n64}/*.eep`, `.sra`, `.fla` (primary), `*_Cont_1.mpk` to `*_Cont_4.mpk` (sidecar), `Unique Game Dir` = `1` (default); `Save/{n64_header}.eep`, `.sra`, `.fla`, `{n64_header}_Cont_1.mpk` to `_Cont_4.mpk`, `Unique Game Dir` = `0` | | emulator source |

`mupen64plus_standalone` covers mupen64plus 2.6 and later, RMG and
simple64, rooted at the emulator's save folder (`SaveSRAMPath`). Each file
is `{name}-{MD5[:8]}`, the name being the first 32 characters of the ROM's
entry in mupen64plus's database, or the header name for a ROM it lacks;
sigil matches the hash and takes any name.

`m64plus_fz` is rooted at the folder the user picked for FZ's game data.
FZ plays from a copy in its private storage and copies each game's folder
there and back when the game starts and stops. A game's folder is
`{header} {country} {md5}`, or the MD5 alone where the file system can't
hold that name; every save in its `SramData/` is the game's.

`project64` is rooted at the folder holding Project64's `Save` folder.
With `Unique Game Dir` on, each game has `Save/{header}-{MD5}/`, its MD5
taken over the ROM in `.n64` order; sigil matches the hash and takes any
name. With it off, the files sit in `Save/` under the header name, which
sigil spells from `n64_header`.

A `*` stands for a name sigil can't spell, so a save that isn't on disk
yet has no name sigil can give it: these rows report no expected files.

## Save formats

The libretro cores (mupen64plus_next, parallel_n64) keep every save type
in one 0x48800-byte `{stem}.srm`: EEPROM, four controller paks, SRAM and
flash at fixed offsets, with unused regions formatted. mupen64plus
standalone, RMG and simple64 keep one file per type (`.eep`, `.sra`,
`.fla`, and one `.mpk` holding four paks); Project64 keeps one `.mpk`
per controller and grows its files sparsely, its gaps reading as 0x00.
Every one of them stores EEPROM and controller paks in the order the N64
reads them, and SRAM and flash with each 32-bit word byte-reversed.
mupen64plus writes a 4 Kbit game's `.eep` at 0x200 bytes and a 16 Kbit
game's at 0x800; the libretro `.srm` always holds 0x800. The emulators
start EEPROM, SRAM and flash as 0xFF (older builds left SRAM 0x00) and
format each controller pak with no notes.

## Sync

The unit is a zip of the save types the game uses, each in the order the
N64 reads it: `eeprom` (0x200 or 0x800 bytes), `pak1` to `pak4` (0x8000
each), `sram` (0x8000) and `flash` (0x20000). Collect takes them from
whichever files the layout names and turns SRAM and flash back to bus
order, so the same save gives the same unit from any of these emulators.
A save type counts as used when it holds a byte other than 0x00 and 0xFF;
a pak, when its index lists a note. EEPROM is 0x200 bytes unless data
lies past 0x200. A game with no used save type has no unit.

Restore writes the request's emulator's own files:

- `mupen64plus_next`, `parallel_n64`: the `.srm`, the unit's types in
  place. A type the unit lacks keeps what is there when the game didn't
  use it, and is blank (0xFF, a formatted pak) otherwise. Bytes after
  0x48800 (parallel_n64's 64DD disk) stay.
- `mupen64plus_standalone`, `m64plus_fz`, `project64`: one file per type,
  `.eep` at 0x800, `.sra`, `.fla`, and a four-pak `.mpk` (Project64:
  `_Cont_<n>.mpk` per pak), each at full size. A new file takes the name
  of a file of the game already there; with none, the name can't be
  spelled and restore refuses with `SIGIL_ERR_NO_TARGET` naming the first
  member. A type's file the unit lacks is removed through `remove`.

Restore also reads a libretro `.srm`, a lone `.eep`, and a zip of any of
these emulators' files, as clients uploaded before sigil. A lone 0x8000
or 0x20000-byte file can't be told apart (SRAM or a pak, flash or four
paks) and is refused with `SIGIL_ERR_UNSUPPORTED_FORMAT`.

## Open items

- Dezaemon 3D's banked SRAM: Project64 keeps up to 0x18000 bytes, mupen64plus and the unit 0x8000.
- parallel_n64's 64DD disk save has no member in the unit; restore keeps it on disk.
- A 16 Kbit game that never wrote past 0x200 reads as 4 Kbit; restore writes 0x800 either way, which both emulators read.
- Controller pak serials differ per emulator and per format; restore keeps an unused pak already there rather than writing a new serial.

- mupen64plus keeps reading a pre-2.6 save named `{database name}.eep` without the hash when one exists; sigil doesn't find those.
- M64Plus FZ with its flat game-data option keeps every game's saves in `GameData/` under database names; sigil doesn't find those.
- Project64 with `Unique Game Dir` off on a cart whose name isn't plain ASCII: the file name depends on the Windows code page, and sigil doesn't find it.
- Project64 with its native save folder moved somewhere not named `Save`.
- parallel_n64 appends a loaded 64DD disk to the `.srm`.
- N64 real-hardware (EverDrive/SummerCart) byte order for SRA/FLA, to confirm against a dump.
