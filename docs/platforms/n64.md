# Nintendo 64

Status: in development
Only emulator research exists for the N64. Sigil reads no N64 header, and no layout row names an N64 core.

## Emulator research

Scope: battery/flash/EEPROM saves and RTC data, not save states. Researched 2026-09-26 against the default branch of each repo (shallow clones). Line numbers refer to those heads and will drift; the function names are the stable anchor.

`{stem}` = content filename without extension. "RA" = RetroArch frontend. RetroArch's own behaviour is in [RetroArch frontend behaviour](gb.md#retroarch-frontend-behaviour-applies-to-every-libretro-core-that-exposes-memory).

### Conversion notes

- **N64**: the libretro blob and the standalone per-type files are the same bytes at fixed offsets (table above). PJ64 uses the same byte order, but its files are sparse and it keeps per-controller `.mpk` files. Real hardware needs a 32-bit swap of SRA/FLA (UNVERIFIED against a physical dump). Detect the save type by which region is not 0xFF, and do not trust file presence alone: libretro always carries all four regions, formatted.

### Save compatibility across releases

- Ocarina of Time: every version saves 0x8000 bytes with a `ZELDAZ` magic and a checksum. NTSC and PAL encode the player name with different character sets (https://wiki.cloudmodding.com/oot/Save_Format).
- Super Mario 64: one EEPROM format, with a language field at 0x12 on PAL (https://bryc.github.io/sm64eep/docs).
- Ocarina of Time NTSC 1.0, 1.1 and 1.2 differ in RAM addresses, not in the save layout, so their saves are likely interchangeable (source above; UNVERIFIED on hardware).
